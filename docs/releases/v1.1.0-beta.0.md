## Migration scope and official 3.6 follow-up

This update complements the `v1.0.0-beta.3` catalog; it is not a replacement
catalog or a sequence of Meteor beta-to-beta migrations. The existing 16
skills, their classifications, bundles and supported Meteor ranges remain.
Most changes add conditional guidance and acceptance cases. Corrections
replace outdated instructions about mandatory npm updates, Babel-only React
Compiler support, Workbox requirements and the browser test harness.

The current concrete upgrade evidence starts at Meteor 3.5.2 and targets
3.6-beta.0. Existing version branches preserve earlier-release behavior, but
do not constitute runtime proof of every older application's direct upgrade.

For the official Meteor 3.6 release:

1. Audit the final release commit and published package versions. Update
   active skill bodies, references and acceptance prompts to the verified
   stable target. Do not blindly strip `-beta` from package versions or retain
   workarounds for beta defects that the official release has fixed.
2. Make the normal migration path an existing Meteor 3.5.x or earlier
   supported release directly to 3.6. Do not require installing successive
   3.6 betas or staging through 3.5.2 merely because the examples started there.
   Preserve necessary source-version prerequisites and package compatibility
   checks; this is not a promise that every older app needs only one command.
3. Cover distinct starting states in the affected acceptance cases and
   disposable runtime checks: a 3.5.x Rspack 1 app, an earlier supported
   Rspack 1 app, and an older Meteor 3 app not yet using Rspack. Keep first
   Rspack adoption separate from upgrading an already-enabled integration.
   Meteor 2 apps also need `migrate-to-meteor-3` for async/API and package
   changes; a bundler migration does not replace that work.
4. Remove obsolete beta-only instructions from active distributable guidance
   and replace beta-targeted cases with stable-targeted cases. Preserve
   older-stable compatibility branches, committed audits, historical changelog
   entries, release handoffs and immutable tags. Those records describe what
   was actually reviewed and tested; they are not the current migration path.
5. Rerun affected behavior, direct-upgrade and installation checks. If the
   stable-target guidance changes after the accepted catalog beta, publish
   and test a new catalog beta before promoting the stable catalog, as required
   by the release workflow.

These are follow-up acceptance requirements, not claims that Meteor 3.6
stable or its catalog version is already published or verified.
