## Additional implementation evidence

- Tagged Rspack constants supply the dependency minimums. The guide's older
  React Refresh examples are not the beta.3 dependency contract. The manual
  npm transition still needs the existing conditional old-peer guidance;
  tagged `tools-core` does not print the flag claimed by the guide.
- The existing bundler optimization reference recommended deleting
  `.meteor/local` for a rebuild. That directory also holds local data, so F01
  replaces this with the existing data-preserving reset boundary.
- MongoDB 8 requires a MongoDB 7 server at FCV 7.0 before upgrade, but keeping
  that FCV does not promise a supported binary downgrade. The
  [official MongoDB 8 upgrade guidance](https://www.mongodb.com/docs/v8.0/release-notes/8.0-upgrade-replica-set/)
  requires support assistance for binary downgrades. Recovery guidance uses
  a verified pre-upgrade backup. Shell presence checks avoid printing
  connection credentials.
- DDP field removal is wire `cleared: ["field"]`, parsed into an undefined
  field value. An explicit null sets a value; absent `fields` does not erase
  retained data. Tagged `ddp-common` parsing and Mongo replication code support
  this distinction.
- A MongoDB-supported projection that Minimongo cannot compile is a driver
  eligibility boundary. Verify fallback before proposing a broader schema or
  publication rewrite.

## Remaining review and stable 3.6 handoff

The repository contract requires an outside contributor to run affected
high-risk cases in Claude Code or Cursor before a PR. That independent
review is pending; these agent-run conversations do not satisfy it. The user
authorized a focused commit and push to `skills/meteor-3.6-beta.3` after the
editorial pass. No PR, tag or catalog publication is part of this handoff.

Meteor implementation and upstream regression tests were inspected, but the
full upstream suites were not run. No retained database was upgraded, no
real old-browser or Cordova device run was performed, and no live OAuth or
production deployment was exercised here. Those environment checks remain
part of the application workflows documented by the skills.

When official 3.6 ships:

1. Audit its exact tag incrementally from this record, including any changed
   runtime, MongoDB, Atmosphere and npm integration versions.
2. Replace active beta commands and pins with verified stable 3.6 values.
   Consolidate transient beta package rows into the stable path; retain
   earlier-release fallbacks and any beta distinction still needed for a
   supported diagnostic.
3. Keep native declarations, Rspack adoption and other optional migrations
   explicit. A stable release must not imply an unrelated provider, bundler,
   database or package-manager switch.
4. Update affected acceptance prompts to stable 3.6 and retain the smallest
   meaningful earlier-version near misses. Rerun high-risk cases and the
   repository/archive checks.
5. Preserve this audit and review as historical evidence. Select the catalog
   release version and publish through `release-publishing` only within a
   separately requested release scope.
